# PageRank: resolve incoming adjacency once per iteration

The selected row is `pagerank` in Ironweaver DB's runtime table. The Rust
core now resolves the projection's incoming CSR once per iteration, rather
than going through the direction branch and lazy `OnceLock` twice per node.
The CSR and its read accessors become crate-visible; the public API, rank
arithmetic, reduction, allocations, cancellation and progress stay unchanged.
Resolving inside the loop preserves the lazy transpose for zero iterations.

## Workload and scope

The baseline source tree is upstream main `227552f54d255ade792d7d6d5a4a91883e93e67b`
(tree `5c15c6c9614e2f37e5e86a72aab15013049cad29`). Its PageRank and projection
sources are identical to DB's pinned core `c69ef5146c5865f2fd160a2df0a13b968d0255a3`.

The harness reproduces the topology, edge weights and IDs generated by
[`ironweaver-db`'s benchmark support](https://github.com/p-sodmann/ironweaver-db/blob/89bb1aacf36a62cdf3e4dfcb6fe2dff560e5ea68/crates/iwdb-server/benches/support/mod.rs):
100,000 nodes, four outgoing edges per node, the same seeded xorshift64*
generator and both random draws per edge. Node payloads are omitted because
PageRank reads only the projection. `db-default` uses a directed, unweighted
projection and default options, exactly as the table's PageRank job does.
It converges in three iterations. `unit-20` and `weighted-20` fix twenty
iterations with `tol=0`; the weighted projection uses the `w` attribute.

These timings cover **PageRank on a prepared projection**. Construction and
the first lazy transpose are warmed up outside the timed samples. The table's
embedded operation also includes database projection, sorting and execution
overhead. The full DB benchmark was not run here; the percentages below must
not be applied directly to its roughly 13–14 ms row or to a different dataset.

## Measurements

AMD EPYC 9V74, Linux x86_64, Rust 1.99.0, Cargo release profile, default
compiler flags. CPU affinity: CPU 0 with one Rayon worker; CPUs 0,1,2 with
three workers. This environment exposes three CPUs but has a two-CPU cgroup
quota (`200000 100000`), which adds noise to parallel measurements.
No builds or tests ran concurrently with the timings.

Four process pairs per configuration, alternating before/after order. Each
process warms up and records five samples of at least 300 ms per case.
Thus each table entry is the median of twenty sample means. Raw samples,
rank fingerprints, iteration counts and paired improvements are retained
in `samples.json` and `summary.jsonl`.

| Workers | Case | Before | After | Median runtime reduction |
| ---: | --- | ---: | ---: | ---: |
| 1 | DB default | 6.357 ms | 5.944 ms | 6.5% |
| 3 | DB default | 4.178 ms | 3.717 ms | 11.0% |
| 1 | Unit, 20 iterations | 40.495 ms | 38.653 ms | 4.5% |
| 3 | Unit, 20 iterations | 27.461 ms | 22.385 ms | 18.5% |
| 1 | Weighted, 20 iterations | 44.572 ms | 41.045 ms | 7.9% |
| 3 | Weighted, 20 iterations | 29.676 ms | 23.742 ms | 20.0% |

Default PageRank improved in all four process pairs for both worker counts:
3.0–11.7% with one worker and 7.2–26.5% with three. The longer controls have
individual negative/outlier pairs, so their median gains are supporting
evidence rather than precise estimates. All measured before/after rank
fingerprints and iteration counts match within each configuration.

A separate four-pair check at 1,000 nodes also improved the medians: default
PageRank from 270 to 236 µs (one worker, 12.6%) and 676 to 566 µs (three
workers, 16.2%). The fixed-iteration controls improved by 9.3–14.2%.
Parallel small-graph samples also have individual negative pairs. These
results and matching fingerprints are retained in `small-samples.json`;
`summary.jsonl` identifies each graph size explicitly.

## Reproduce

From the PR checkout, build and freeze the same harness against both source
versions. Use one Rust toolchain and no differing `RUSTFLAGS`.

```sh
cargo build -p ironweaver-core --example pagerank_bench --release
cp target/release/examples/pagerank_bench /tmp/iw-pagerank-after
git worktree add --detach /tmp/iw-pagerank-before 227552f54d255ade792d7d6d5a4a91883e93e67b
cp crates/ironweaver-core/examples/pagerank_bench.rs /tmp/iw-pagerank-before/crates/ironweaver-core/examples/
cp Cargo.lock /tmp/iw-pagerank-before/Cargo.lock
cargo build --manifest-path /tmp/iw-pagerank-before/Cargo.toml -p ironweaver-core --example pagerank_bench --release --target-dir /tmp/iw-pagerank-before-target
python performance_results/pagerank-2026-10-09/compare.py /tmp/iw-pagerank-before-target/release/examples/pagerank_bench /tmp/iw-pagerank-after --cpus 0,1,2 --output /tmp/iw-pagerank-samples.json
```

On macOS omit `--cpus`; `--threads`, `--nodes` and `--pairs` can be overridden.
For your database and data, update the `ironweaver-core` git revision to the
PR's head, update the lockfile, then repeat your original benchmark with the
same dataset, hardware, flags and worker count. For the table's synthetic
workload the command is:

```sh
IWDB_BENCH_NODES=100000 cargo bench -p iwdb-server --bench graph -- analytics/pagerank
```

## Correctness

All 163 Rust tests and six doc tests passed before and after. The added test
compares fixed-iteration results against an independent sequential push
formulation on 1,301-node sparse multigraphs, with one/three workers,
weighted/unweighted edges, dangling nodes, personalization, damping values
0/0.85/1, and 0/1/2/5/20 iterations. Existing tests cover dense reference
results, projection directions, cancellation, progress and invalid options.
Additional integration and lint results are recorded in `validation.txt`.
