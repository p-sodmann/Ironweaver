# Performance change workflow

Run every available Ironweaver benchmark workload before and after a performance
change **on the same machine**, with the same compiler, lockfile, Python
interpreter, dependencies, build profile, CPU affinity and thread counts.
Historical tables, plots, another machine, or a CI runner are not a timing
baseline. Keep the bindings unchanged when optimizing the core.

1. Build separate baseline and candidate artifacts. Keep them frozen while
   measuring. Use the same release command and copied `Cargo.lock` for both.
2. Run the complete workload inventory below. Add a focused benchmark for the
   proposed change, including unaffected controls and cases where an optimization
   might add work (for deletion: few edges into large hubs, dense neighborhoods,
   unrelated surviving edges, self-loops and small graphs).
3. Alternate baseline/candidate order across independent process pairs. For the
   broad suite, interleave individual operations and wait at barriers so one
   revision cannot prepare another operation during its counterpart's timer.
   Run no builds, tests or other benchmarks concurrently.
4. Retain raw samples and artifact hashes. Use process-paired confidence
   intervals; inner repetitions are not independent observations. Report
   inconclusive differences as inconclusive. A possible slowdown needs an
   independent repeat before acceptance, especially when screening many metrics.
5. Run correctness tests, formatting and Clippy, then include the complete
   before/after report and limitations in the PR. Keep the PR a draft while a
   measured regression is unresolved. Timing assertions do not belong in shared
   CI runners.

## Workload inventory

| Source | Required Ironweaver workloads |
|---|---|
| `compare_networkx.py` | Both default sizes (1,000/5,000 and 20,000/100,000): construction, traversals, paths and batches, fresh projections, analytics, embeddings/walks, subgraphs, mutation, counting and JSON I/O; includes the individually looped batch-path calls. Preserve its NetworkX reference assertions. |
| `compare_libraries.py` | Facebook, GitHub and Kronecker defaults: construction plus every applicable algorithm with fresh and reused projections. Keep the existing directed-only restrictions and `nodes * edges <= 5e9` exact-betweenness budget, and record every exclusion. Exact betweenness keeps the original one-run-per-process rule. |
| `compare_networkx_memory.py` | Both default sizes (10,000/50,000 and 100,000/500,000): resident graphs with/without attributes, JSON load/save peaks, and JSON/native-binary file sizes. Use fresh child processes and a working peak-RSS reset. |
| `bench_remove_node.rs` / `compare_remove_node.py` | All deletion fixtures, including parallel edges in both directions, mixed survivors, ordinary/shuffled stars, leaves, two large hubs, sparse fan-out and dense neighbors. |

Run the other graph libraries when investigating competition between libraries.
A revision comparison needs both Ironweaver revisions to execute the same
workloads; repeating unrelated competitors is not required. Archived CSV/image
reports under `performance_results/` have no executable benchmark sources in
this checkout and are not used for cross-machine comparisons.

## Broad comparison

Activate the development environment with Rust, Python, Maturin, uv and the
benchmark dependencies installed. Generate the ignored `Cargo.lock` if needed,
then build two committed revisions into a fresh directory:

```bash
bash benchmarks/build_revision_pair.sh BASELINE_REF CANDIDATE_REF /tmp/revision-builds
```

The builder copies one lockfile and the candidate's focused benchmark source to
both source archives. It builds release wheels and core executables serially,
and records build metadata. Finish all compilation before measuring:

```bash
python benchmarks/compare_revisions.py /tmp/revision-builds/baseline /tmp/revision-builds/candidate \
  --pairs 6 --repeats 3 --reference-cache /tmp/reference-cache \
  --output /tmp/revision-results.json
```

The runner checks that all workers share the same boot fingerprint, runtime,
affinity and thread count. Optional `build.json` files next to the packages
allow it to additionally require matching compiler, lockfile, binding-source
hashes and build flags. It records extension hashes for every process.

The reference cache contains locally generated NetworkX results, keyed by the
machine/runtime and benchmark source. It is primed before collecting paired
samples; all original reference assertions still run. Ironweaver results and
timings are never cached. Only use a cache generated by this runner.

On Linux the memory suite writes `5` to its own `/proc/self/clear_refs` to reset
its peak-RSS counter. If a sandbox disallows that, run this benchmark with the
permission required for that single operation. An unsupported reset is a
failure, not a passing memory check.

For the focused core comparison, build the same example on both revisions and
copy each executable to a separate path, then run:

```bash
python benchmarks/compare_remove_node.py /tmp/revision-builds/baseline/bench_remove_node /tmp/revision-builds/candidate/bench_remove_node \
  --pairs 20 --samples 3 --output /tmp/deletion-results.json
```

See `performance_results/` for the measured report and raw samples. Include
commands, machine/build metadata, all workload outcomes and any exclusions
when reporting a new optimization loop.

`confirm_revision_results.py` independently repeats the five slower timings
from this change's broad screen with the same datasets and operations. Use it
to reproduce this report's confirmation, rather than as a replacement for the
complete suite:

```bash
python benchmarks/confirm_revision_results.py /tmp/revision-builds/baseline /tmp/revision-builds/candidate \
  --pairs 20 --repeats 7 --output /tmp/confirmation.json
```

The focused runner also accepts `--cases shape:size,...`, `--batch` and
`--small-batch` for independent control repeats. Keep the initial complete
inventory and every repeat's raw samples in the report.

## Construction and subgraph revision controls

The revision builder also freezes `construction_bench` and `traversal_bench`
from the candidate into both builds. Core construction isolates timed work from
node setup and graph destruction, except that subgraph-result destruction is
included. Controls cover node insertion, duplicates, stale endpoints, neighbor
iteration, self-loops, parallel/typed/explicit-ID edges and small subgraphs.

```bash
python benchmarks/compare_construction.py BUILD/baseline/construction_bench BUILD/candidate/construction_bench --output construction.json
python benchmarks/compare_traversal_revisions.py BUILD/baseline/traversal_bench BUILD/candidate/traversal_bench --output traversal.json
python benchmarks/compare_construction_threads.py BUILD/candidate/construction_bench --output threads.json
```

The thread control inserts edges into four independent Rust graphs, alternating
one/two-thread process pairs. It does not imply that Python graph mutation
releases the GIL or that a single graph can be mutated concurrently.
`compare_revisions.py --serial` runs entire workers serially, including all
preparation between timed operations. Finish builds and correctness checks
before starting any benchmark runner. Preserve primary and independent repeat
samples separately; confidence intervals are pointwise, not simultaneous.

For the unchanged-binding edgeless filter/BFS control, use
`compare_edgeless_bindings.py BUILD/baseline BUILD/candidate`. Its source graph
is prepared outside timing, and samples batch 128 calls including result
destruction. `serial_revision_controller.py` checkpoints each complete broad
worker and pair; it reuses only complete pairs after interruption. Use it with
the same `--data` and `--reference-cache` as the original runner.

`analyze_construction_performance.py --raw RAW --out REPORT` computes paired
Student-t intervals on process log ratios and produces the two PNG overviews.
`repeat_construction_regressions.py --summary REPORT/summary.json` launches
independent confirmations of every primary positive interval. The core
confirmation repeats the full traversal context; selected general-operation
confirmations preserve selected timing while running required references once.
Primary and repeat estimates stay separate, and new repeat-only signals must
remain explicit. Run all commands under one exclusive lock without overlapping
builds, tests or benchmark workers.

## Projections from arrays

`compare_from_arrays.py` times `Projection.from_arrays` against building the
same projection through a Vertex (`add_nodes`, `add_edges`, `project`) on a
grid with random obstacles (about 180k nodes and 700k directed edges by
default; `--side`, `--obstacles`, `--repeats`), and checks that both
projections agree. It needs numpy.

```bash
python benchmarks/compare_from_arrays.py
```

## A* on a projection

`compare_astar.py` builds a 4-connected grid with `Projection.from_arrays`
(about 180k tiles and 700k directed edges by default; entering a tile costs
1, or 2 to 4 for a fraction `--rough` of the tiles; `--side`, `--obstacles`,
`--trips`) and times `Projection.shortest_paths` per trip with "dijkstra"
and with "astar" (Manhattan and Euclidean estimates), one call per trip and
one batch call, checking that all costs agree. Set `RAYON_NUM_THREADS=1` to
time a single thread. It needs numpy.

```bash
RAYON_NUM_THREADS=1 python benchmarks/compare_astar.py
```

## Changing projection weights in place

`compare_set_weights.py` builds the grid of `compare_astar.py` and times
`Projection.set_weights` for batches of 1 to 10,000 tiles (the edges into
them made impassable, then restored), with and without the reversed
adjacency built, next to rebuilding the projection with
`Projection.from_arrays`; it checks that the updated projection finds the
same paths as a rebuilt one. It needs numpy.

```bash
python benchmarks/compare_set_weights.py
```


## NodeView adjacency queries

`compare_nodeview_adjacency.py` compares native degree counts, neighbor existence
checks and neighbor ID sets with equivalent Python edge-snapshot queries on the
same graph and extension. It checks results, alternates measurement order, and
reports median times for degrees 8 and 1,000 as JSON. Use an optimized build;
these are local microbenchmarks rather than whole-application speedups.

```bash
python benchmarks/compare_nodeview_adjacency.py
```


## Tiny graph binary bytes

`compare_binary_bytes.py` measures binary bytes encoding/decoding and atomic file
save/load for 0, 1, 10 and 100 nodes, with two edges per node. Build/install an
optimized extension first. It emits raw repeat samples as JSON. File saves
include fsync/rename; bytes encoding excludes storage durability costs.

```bash
python benchmarks/compare_binary_bytes.py
```

`compare_binary_compression.py` compares raw binary bytes, gzip/zlib/raw DEFLATE,
and optional Zstandard/LZ4, measuring size, codec costs and graph round trips.
Install `zstandard` and `lz4` only to benchmark those optional codecs. See
`performance_results/tiny_binary/compression/REPORT.md` for measurements and limits.

## Durable binary BLOB persistence

`persist_binary.py` compares encoding/compression plus SQLite WAL commits with
`synchronous=FULL`, and fetching/decompression plus graph reconstruction. It
tests one or 100 graphs per commit, changing one or all scores, and verifies
reopen/read-back. Select the real target filesystem; `/tmp` may be RAM-backed.

```bash
python benchmarks/persist_binary.py --directory /path/on/target/filesystem --output results.json
```

Correctness and batch rollback run in `tests/test_binary_persistence.py`; there
are no timing assertions. See `performance_results/tiny_binary/persistence/REPORT.md`.
SQLite results do not characterize Ironweaver DB's WAL or server behavior.

## Tiny graph load cache

`compare_binary_decode.py` profiles complete binary/JSON load lifecycles and an
encoding control for ordinary, unique-key, nested, embedding, indexed and Unicode
graphs. `compare_decode_controls.py` independently repeats selected encoding and
numeric JSON controls. Run frozen artifacts in alternating independent processes.
See `performance_results/tiny_decode/REPORT.md` and raw measurements.
